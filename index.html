red specification · 2026-07-10

A TypeScript/Bun library for building idempotent devops CLIs: desired state in YAML, workflows as step graphs threaded by one plain object, Selmer-style template-scaffolded configuration, OpenTofu as the infrastructure runner, and Ansible for SSH provisioning.

1. Philosophy

  • red is a library. Users define steps, wiring, and workflows in their own project; red supplies the engine, infrastructure helpers, template rendering, advice, and CLI plumbing.
  • Everything is one object. Desired state is YAML loaded into opts. Every step reads and returns that plain object, possibly enriched with observed reality such as OpenTofu outputs or Ansible recaps.
  • Idempotent apply. There is no plan phase in red itself. Re-running the same event should converge. create and delete are conventions; the event set is open.
  • Errors are values. Steps report outcome with "red/exit". Thrown exceptions are caught at step boundaries and converted into opts values, so failures can route through nextFn and joins like any other result.
  • TypeScript/Bun only. red is the Bun implementation of the green workflow model. A green project ports mechanically by replacing Clojure keywords/namespaces with namespaced string keys and TypeScript modules.

2. Naming, desired state & the opts contract

Everything called green in the original model is called red here. Clojure keywords become namespaced string keys, and keyword values become plain strings.

greenred
:green/exit"red/exit"
:green.scaffold/written"red.scaffold/written"
green.ednred.yml
./green./red, a Bun script
green.workflowred/workflow
:zk/servers"zk/servers"
:create"create"

The base type is open: Opts = { [key: string]: any }. red reserves red/* and red.*/* keys; project and library state should live under namespace-like keys such as "zk/servers", "once/workdir", or "tofu/outputs".

KeyMeaning
"red/event"First positional CLI argument: "create", "delete", "rotate", etc.
"red/dry-run"Stamped by --dry-run; dry-run advice uses it to skip named steps.
"red/exit"Integer outcome. Missing means success and is normalized to 0 after a step returns.
"red/err"Error message when "red/exit" is positive.
"red/trace"Stack trace string when a thrown exception is converted to a red failure.
"red/step"Current step name, stamped before each step runs. Advice such as progress reads it.
"red/branches"Array of per-branch result objects at a join or collapsed failed fork. Sort by your own key if order matters.
"red.workflow/inherited"Private advice-inheritance payload. It is stripped from public step and workflow results.
Step input is frozen. The engine deep-freezes opts at each step boundary. Steps should return new objects with spread syntax instead of mutating input. If a step throws, the failure opts are built from the frozen input so partial mutation cannot leak.

3. Steps and errors

A step is a plain function (opts) => opts | Promise<opts>, named by a namespaced string such as "zk/node". The name anchors wiring, logging, CLI slices, joins, and advice.

  • A returned plain object without "red/exit" is treated as success and stamped with 0.
  • Returning a non-object, array, or missing return is a step failure.
  • Throwing is allowed: the runner catches the exception and returns "red/exit": 1, plus "red/err" and "red/trace".
  • Throw new StepError(message, {exit}) when a step or advice wants to choose a specific failure exit code.
  • Steps usually branch on "red/event". Library steps use the convention “any non-"delete" event creates/applies; "delete" destroys/deprovisions.”
  • Steps must await everything they start. A stray un-awaited rejection cannot be attributed to a branch; execCli reports unhandled rejections and exits nonzero.
import { StepError, type Opts } from "red/workflow";

const check = (opts: Opts): Opts => {
  if (!opts["app/name"]) {
    throw new StepError("app/name is required", { exit: 2 });
  }
  return { ...opts, "red/exit": 0 };
};

The helper failed(opts) is true when (opts["red/exit"] ?? 0) > 0. Without a nextFn, a failed step produces no successors and that branch halts. With a nextFn, cleanup, retries, and alternate paths are ordinary user routing.

4. Workflows: wireFn, nextFn, and composition

import { workflow, run, step, type Opts } from "red/workflow";

const wf = workflow({
  start: "zk/start",          // required
  end: undefined,             // optional inclusive slice boundary
  wireFn,                     // required static graph
  nextFn,                     // optional dynamic router
});

const result = await run(wf, { "red/event": "create" });

wireFn — the static graph

wireFn(step, runOpts) returns a tuple containing the step function followed by its default successors for this run. runOpts is the initial opts passed to run, so the graph may depend on stable run-level inputs such as "red/event".

const wireFn = (step: string, runOpts: Opts) => {
  switch (step) {
    case "zk/start":
      return [startStep, "zk/node"] as const;
    case "zk/node":
      return [nodeStep, "zk/zoo-cfg"] as const;
    case "zk/zoo-cfg":
      return [zooCfgStep] as const;
    case "ci/fork":
      return [forkStep, "ci/a", "ci/b"] as const;
  }
};

Multiple successors mean a static fork. The same graph is used for join scheduling, so keep the happy path visible even when nextFn adds dynamic behavior. Do not base wireFn on values produced after the run starts; route those cases in nextFn.

nextFn — the dynamic router

When present, nextFn decides successors after each non-end step:

nextFn(step, defaultNext, opts) // => iterable of [nextStep, opts] pairs
  • Return [], null, or undefined to terminate a branch; return one pair to continue; return many pairs to fan out in parallel.
  • Because it sees the step result, including "red/exit", nextFn can route failures to cleanup, retry, or halt.
  • Without nextFn, positive "red/exit" stops that path; otherwise the default successors run.
const nextFn = (step: string, defaultNext: string[] | null, opts: Opts) => {
  if ((opts["red/exit"] ?? 0) > 0) return [];
  if (step === "zk/start") {
    return opts["zk/servers"].map((server: unknown) => [
      "zk/node",
      { ...opts, "zk/server": server },
    ] as const);
  }
  return (defaultNext ?? []).map((s) => [s, opts] as const);
};

Composition — a workflow is a step

step(subWorkflow)
step(subWorkflow, {
  inFn:  (opts) => subOpts,
  outFn: (opts, subResult) => parentResult,
})
  • The sub-workflow's result is just a step result, so failures propagate through parent routing naturally.
  • With default inFn, ambient keys such as "red/event" and "red/dry-run" flow into the child. If custom inFn builds opts from scratch, carry the ambient keys the child needs.
  • Advice inheritance is preserved even when inFn rebuilds opts from scratch. This lets a parent impose dry-run, backend, audit, or provider advice on embedded workflows by flat step name.

Slices

The optional end step is inclusive: it runs, then the workflow stops. The CLI's --start and --end override workflow boundaries for safe idempotent slice runs.

5. Parallelism, fan-out & joins

  • Static fork: wireFn lists several successors.
  • Dynamic fan-out: nextFn returns several [step, opts] pairs.
  • Join: branches from different origins that converge on the same step run that step once, using the fork-point opts plus "red/branches".
  • Same-origin fan-out: same-step entries from one fan-out parent run independently instead of joining, which is how dynamic N-way item processing works.
  • Failure: a failed branch inside a fork lets siblings finish their current step, collapses the fork, skips the join, and propagates the worst exit with all branch results under "red/branches".
Join detection. Convergence is by flat step name. The scheduler waits while another live branch can statically reach the same step through this run's wireFn graph; dynamic detours not visible in that graph may require explicit routing care.

Scheduler algorithm in plain English

  1. Start with one live task: run start with the initial opts.
  2. Loop while work remains, tracking live branches and finished terminals.
  3. Group live entries by step.
  4. Run only ready steps: if a different live branch can still reach a step, wait so it can join.
  5. Run ready units concurrently with promises.
  6. Expand each result into zero, one, or many next entries.
  7. When different origins arrive at one step, run a join unit once.
  8. Collapse failed forks before scheduling more work.
  9. Finalize to one opts object: first failure wins, otherwise the last success.

Independent pipelines inside a fan-out

When nextFn fans out N branches and each branch traverses multiple steps in sequence, converging on the same second step can be interpreted as a join. Wrap the per-item pipeline in a sub-workflow with step(subWorkflow) when the count is dynamic — N items, N nodes, N tenants.

const pipelineWf = workflow({
  start: "item/validate",
  wireFn: (step) => {
    switch (step) {
      case "item/validate": return [validate, "item/transform"] as const;
      case "item/transform": return [transform, "item/load"] as const;
      case "item/load": return [load] as const;
    }
  },
});

const parentWireFn = (step: string) => {
  switch (step) {
    case "batch/start": return [start, "batch/process"] as const;
    case "batch/process": return [step(pipelineWf)] as const;
  }
};
When you don't need step. If the number of branches is fixed and known at design time, distinct step names work: "deploy/staging" and "deploy/production" never converge, so they run independently without a sub-workflow.

6. Advice

Advice wraps step functions without changing graph wiring. Registries are immutable workflow data; adding/removing advice returns a new workflow.

import { adviceAdd, adviceAddAll, adviceRemove, adviceRemoveAll } from "red/workflow";

const advised = adviceAdd(wf, "zk/node", "before", "app/backend", writeBackend);
const withProgress = adviceAddAll(advised, "around", "app/progress", progress);
const withoutBackend = adviceRemove(withProgress, "zk/node", "app/backend");
const quiet = adviceRemoveAll(withoutBackend, "app/progress");
HowEffectUse cases
"around"advice(base, opts)Dry-run, retry, timing, locks; may call the base zero, one, or many times.
"override"advice(opts), base never runsReplace/stub a step.
"before"Advice side effect, then base; advice return ignoredSetup: backend files, inventories, directories, locks.
"after"Base, then advice side effect; base return flows outAudit, metrics, notifications, cleanup.
"before-while"Continue inward only while advice returns truthyValidation and policy gates.
"before-until"Use advice result when it is truthy; otherwise baseFast path / already converged no-op.
"after-while"Run advice only when the inward result is red-trueSuccess-only verification or registration.
"after-until"Use inward result if red-true; otherwise advice fallbackRecovery or alternate result.
"filter-args"Transform opts before baseNormalize/scope inputs.
"filter-return"Transform base resultNormalize/enrich outputs.

Advice functions may be sync or async; composition awaits each layer. For while/until combinators, red uses Clojure-style truthiness: only null, undefined, and false are falsy, so 0 and "" are truthy. For after-while and after-until, a step-result object is true when "red/exit" is missing or zero and false when it is positive.

Stacking is Emacs-like. At equal depth, newest advice is outermost. depth (-100..100, default 0) overrides add order: lower depths run farther outside, higher depths farther inside. Re-adding the same id replaces the old entry and moves it according to the new sequence/depth.

Advice inheritance through step. The enclosing run stamps its effective advice into opts under a private key, and the nested run merges that advice over the child's own registries. Ancestor entries are outermost at equal depth; same-id ancestor entries replace child entries. Use advicePlan(wf, step) or advicePlan([parent, child], step) to inspect the composed stack.

7. red.yml and validation gates

The CLI reads red.yml by default (override with -f/--file), parses it with Bun.YAML.parse, stamps the lifecycle event, and passes the resulting object to run.

zk/workdir: work
zk/servers:
  - {id: 1, name: zk1, ip: 10.0.0.1}
  - {id: 2, name: zk2, ip: 10.0.0.2}
  - {id: 3, name: zk3, ip: 10.0.0.3}

# Quote version-like values; YAML would parse 3.10 as a number.
zk/version: "3.10"
  • Namespaced keys such as zk/servers parse unquoted in Bun YAML.
  • YAML 1.2 treats values like no as strings in Bun 1.3.14, but quote anything ambiguous in public examples.
  • Validation should happen at boundaries and/or as before-while gates.

schemaGate(schema, {exit?}) builds a Zod-backed before-while advice. Gates validate and return the original opts; they must not replace opts with the parsed output because Zod can strip unrelated namespace keys.

import { z } from "zod";
import { schemaGate } from "red/gates";
import { adviceAdd } from "red/workflow";

const stateSchema = z.object({
  "zk/servers": z.array(z.object({ id: z.number(), name: z.string() })),
}).passthrough();

const gated = adviceAdd(wf, "zk/start", "before-while", "zk/state-schema", schemaGate(stateSchema));

8. The scaffolding DSL and renderer

scaffold(opts, specs) materializes or removes a flat sequence of file specs:

import mainTf from "./templates/main.tf" with { type: "text" };
import { scaffold } from "red/scaffold";

const specs = [{
  template: { name: "zk/main.tf", content: mainTf },
  target: "{{workdir}}/nodes/{{node.id}}/main.tf",
  data: { workdir: opts["zk/workdir"], node },
}];

return scaffold(opts, specs);
KeyMeaning
template{name, content}. The content should come from a Bun text import. There is no runtime template lookup.
targetOutput path, itself rendered with the same renderer against data.
dataTemplate data for both body and target path.
optsOptional render options, including delimiter overrides.

On "red/event": "delete", the same specs name targets to remove. The implementation removes files and prunes the immediate parent directory if it becomes empty. Return keys are "red.scaffold/written" or "red.scaffold/deleted".

The renderer implements the Selmer-compatible subset red exercises: variables, dotted paths, missing values as empty, HTML escaping by default, safe, sort(attribute='...'), for loops, and delimiter overrides (tagOpen, tagClose, filterOpen, filterClose). Delimiter overrides are useful when scaffolded Ansible files must preserve Jinja2 {{ }} and {% %}.

9. OpenTofu integration

import { tofuStep, localBackendAdvice, s3BackendAdvice } from "red/tofu";

const applyNode = (opts: Opts) =>
  tofuStep(opts, { dir: `${opts["zk/workdir"]}/node-${opts["zk/id"]}` });
  • Any non-"delete" event: tofu init -input=false -no-color, then tofu apply -auto-approve -input=false -no-color, then tofu output -json.
  • "delete": tofu init, then tofu destroy -auto-approve -input=false -no-color.
  • Apply outputs are parsed to {name: value} and assoc'd under "tofu/outputs" by default. If you override outputKey, keep it namespaced.
  • Non-zero process exits become "red/exit" and "red/err".
  • All subprocesses go through runtime.exec, which tests can stub.

Backends are not hardwired. backendAdvice writes backend.tf.json for any backend type and config map (or function of opts), preserving native JSON values and nested collections. Helpers ship for local, S3, and GCS.

const withBackend = adviceAdd(
  wf,
  "zk/tofu",
  "before",
  "zk/backend",
  localBackendAdvice((opts) => `${opts["zk/workdir"]}/node-${opts["zk/id"]}`),
);

10. Ansible integration

import { ansibleStep, inventoryAdvice } from "red/ansible";

const provision = (opts: Opts) =>
  ansibleStep(opts, {
    dir: "ansible",
    inventory: "inventory.ini",
    privateKey: "work/ssh/id_ed25519",
    user: "root",
    hostKeyChecking: false,
  });
  • Any non-"delete" event runs the create playbook (create.yml by default); "delete" runs the delete playbook (delete.yml by default). Override with playbooks.
  • Options map to ansible-playbook: inventory, privateKey, user, extraVars (JSON -e), and hostKeyChecking: false (exports ANSIBLE_HOST_KEY_CHECKING=False).
  • On success, PLAY RECAP is parsed into per-host counters under "ansible/recap" by default; override with namespaced recapKey.
  • inventoryIni renders deterministic INI from {group: {hosts: [{name, vars}], vars}}.
  • inventoryAdvice is a before advice that writes an inventory file from data or a function of opts, mirroring OpenTofu backend advice.
  • ansibleWithSpec scaffolds then runs on create, and runs then removes scaffolded files on delete.

11. Dry-run, progress, and runtime

Dry-run and progress are advice layers, not special cases in the engine.

  • dryRun.advise(wf, steps) attaches around advice id "red.dry-run/skip" to named steps. With "red/dry-run", it logs dry-run: would run <step> (<event>) and returns success without calling the step.
  • progress.advise(wf) attaches all-step around advice id "red.progress/progress". It logs >>> <step> (<event>) before and <<< <step> (<n>ms) after, reading "red/step".
  • runtime.exec(cmd, {cwd, env}) is the single subprocess seam used by OpenTofu and Ansible helpers.
  • runtime.log(...args) is the single log seam used by dry-run and progress.
import * as dryRun from "red/dry-run";
import * as progress from "red/progress";

const wf2 = progress.advise(
  dryRun.advise(wf, ["zk/scaffold", "zk/tofu", "zk/ansible"]),
);

12. The CLI and ./red launcher

./red <event> [-f|--file red.yml] [--start step] [--end step] [--dry-run]

./red create
./red delete -f prod.yml
./red create --start zk/node --end zk/node
./red create --dry-run
  • The first positional argument is stamped into "red/event".
  • --start and --end override workflow boundaries.
  • --dry-run stamps "red/dry-run": true; it has an effect only on steps advised with red/dry-run.
  • Missing event, missing state file, YAML parse errors, or other CLI config errors return exit 2 from runCli.
  • execCli prints "red/err" and "red/trace" to stderr and exits with "red/exit".

A project's ./red is a self-contained Bun script: executable, no build step, no generated launcher. It owns the workflow definition, advice wiring, execCli call, and text imports of local templates.

#!/usr/bin/env bun
import { execCli, workflow, type Opts } from "red";

const start = (opts: Opts): Opts => ({ ...opts, "app/seen": true });

const wf = workflow({
  start: "app/start",
  wireFn: (step) => {
    switch (step) {
      case "app/start": return [start] as const;
    }
  },
});

if (import.meta.main) {
  await execCli(wf);
}
Consumer imports. Once red is published to npm, external consumers should use version-pinned imports such as import { workflow } from "red@x.y.z". Until then, use a minimal package.json with a pinned git dependency and import from red; do not recommend unpinned Bun auto-install imports.

14. Testing strategy

The suite runs with bun test; TypeScript checking runs with bun run typecheck. Test files are discovered as test/*.test.ts.

  • test/workflow.test.ts covers linear runs, errors, slices, event-specific static graphs, dynamic routing, fork/join, failure collapse, concurrency, and composition.
  • test/advice.test.ts covers every advice combinator, ordering/depth, all-step advice, removal/replacement, and inheritance through step.
  • test/scaffold.test.ts covers template rendering, create/delete symmetry, and idempotent rendering.
  • test/tofu.test.ts and test/ansible.test.ts stub runtime.exec instead of shelling out.
  • test/cli.test.ts, test/dry-run.test.ts, test/progress.test.ts, and test/gates.test.ts cover CLI flags, advice helpers, logging, and Zod validation gates.
  • test/zookeeper.test.ts is the e2e suite: if tofu is on PATH, it runs real render/apply/output/destroy cycles over HCL containing only locals and output blocks.
  • test/floci-zookeeper.test.ts is opt-in with RED_FLOCI_E2E=1 because it requires Docker/floci, Ansible, provider downloads, and minutes of runtime.
