Coding agents write deployment code directly: the provider CLI and API calls, the ordering, the retries and the checks that Terraform and Ansible once had to declare. The colors are the foundation for that code: three workflow SDKs, Green, Red and Blue, that share one model in Clojure, TypeScript and Python.

red is the TypeScript/Bun color. Build your own package on it, or start from PocketDeploy, the starter package built on Blue. Steps call cloud CLIs or APIs directly; red has no OpenTofu or Ansible integration.

1. Philosophy

  • One model, three languages. Green is canonical; red and blue port its behaviour, locked by their test suites. A project ports between colors by mechanical rename: :green/exit → "red/exit" → "blue/exit", ./green → ./red → ./blue.
  • Plain data, plain functions. State is one open object; a step is a function from it to it. No class hierarchy, no resource DSL, no state engine.
  • Code, written by agents. A step calls the provider's CLI or API itself. The program is cheap to write and readable to review; nothing is hidden behind a second language.
  • Cross-cutting behaviour is advice. Dry-run, progress, validation and retries wrap steps; the engine stays small.
  • Errors are values. Failures flow through the graph as data and can be routed, not thrown past the caller.
  • No runtime dependencies. red needs Bun and nothing else.

2. The opts contract

All cross-step state is one plain object threaded through the graph. The type is open (interface Opts { [key: string]: any }); steps read the keys they need and pass everything else through untouched.

  • The engine owns red/* and private red.*/* keys: "red/exit", "red/err", "red/trace", "red/event", "red/dry-run", "red/step", "red/branches", "red/state-file", and the private "red.workflow/inherited".
  • Project data uses its own namespace-like keys ("app/servers"). Desired-state inputs that may be overridden from the environment stay flat and kebab-case (do-token).
  • Step input is recursively frozen at each step boundary. Map, Set, Date, typed arrays, class instances and accessor properties fail before the step runs. Steps return new objects with spread syntax.

3. Steps and errors

A step is (opts) => Opts | Promise<Opts>, named by a namespaced string such as "app/node".

  • "red/exit": 0 succeeded, >0 failed; failed(opts) tests it. A successful step that sets no exit gets 0 stamped.
  • The step boundary is the exception firewall: any throw or awaited rejection becomes "red/exit", "red/err" and "red/trace" on the step's input opts.
  • throw new StepError(message, { exit }) chooses the exit code; any other throw is exit 1.
  • A non-object return (a forgotten return) fails through the same contract.
  • Without a nextFn, a failed step has no successors and its branch halts. With one, routing a failure to cleanup or retry is user logic.
  • Exit 2 is reserved for usage and configuration errors.
  • Steps must await everything they start; execCli turns a stray unhandled rejection into a nonzero process exit.

# A step that calls a CLI directly

async function sh(cmd: string[]): Promise<string> {
  const proc = Bun.spawn(cmd, { stdout: "pipe", stderr: "pipe", stdin: "ignore" });
  const [out, err, exit] = await Promise.all([
    new Response(proc.stdout).text(), new Response(proc.stderr).text(), proc.exited,
  ]);
  if (exit !== 0) throw new StepError(`${cmd.join(" ")} failed: ${err.trim()}`, { exit });
  return out.trim();
}

const host: StepFn = async (opts) => ({ ...opts, "hello/host": await sh(["uname", "-sm"]) });

4. Workflows: wireFn and nextFn

workflow({ start, end?, wireFn, nextFn? }) builds an immutable workflow value. Every constructor and advice function is pure, so workflows can be shared and branched freely.

  • wireFn(step, runOpts) => [fn, ...nextSteps] | undefined is the static happy-path graph. runOpts is the run's initial opts, stable for the whole run, so the graph may depend on "red/event" without flapping.
  • nextFn(step, defaultNext, opts) => [[nextStep, opts], ...] routes dynamically: fan-out, conditional branches, error paths. Returning [] or null ends the branch.
  • end is an inclusive slice boundary: the step runs, then the workflow stops.
  • step(subWorkflow, { inFn?, outFn? }) embeds a workflow as an ordinary step. inFn shapes the sub-workflow's opts; outFn(opts, subResult) merges the result back (default: the sub-result).
  • run(wf, opts) runs a workflow and returns the final opts.
const wf = workflow({
  start: "app/start",
  wireFn: (step) => {
    switch (step) {
      case "app/start": return [start, "app/node"];
      case "app/node": return [node, "app/join"];
      case "app/join": return [join];
    }
  },
  nextFn: (step, defaultNext, opts) => {
    if (failed(opts)) return [];
    if (step === "app/start") {
      return opts.servers.map((s: unknown) => ["app/node", { ...opts, "app/server": s }] as const);
    }
    return (defaultNext ?? []).map((s) => [s, opts] as const);
  },
});

5. Parallelism and joins

  1. Live branches are grouped by step. A step is blocked while another live branch could still reach it along static wireFn edges.
  2. Same-step entries from the same fan-out run individually; entries converging from different origins join: the step runs once with the fork-point opts plus "red/branches", the array of branch results.
  3. Multiple successors fork into real parallel promises.
  4. When a branch fails inside a fork, in-flight siblings finish their current step, then the fork collapses: the join is skipped and a terminal carries the worst exit, its error and trace, and "red/branches". Collapse cascades outward through nested forks. Equal exit codes select the first incoming branch.
  5. A join whose incoming branches already include a failure is skipped the same way.
  6. Final result: no terminals → {"red/exit": 0}; one → it; several → the first failed one, else the last successful one.

6. Advice

Emacs nadvice-style combinators, scoped to a workflow value:

howbehaviour
aroundfn(base, opts) decides whether and how to call the step.
overridefn(opts) replaces the step.
before / afterfn(opts) runs before or after; its return is ignored.
before-whileRuns the step only if fn(opts) is truthy; otherwise returns that value.
before-untilReturns fn(opts) if truthy; otherwise runs the step.
after-whileIf the step succeeded, returns fn(opts); otherwise the step's result.
after-untilIf the step failed, returns fn(opts); otherwise the step's result.
filter-argsThe step receives fn(opts).
filter-returnThe result is fn(stepResult).
  • adviceAdd(wf, step, how, id, fn, props?) targets one step; adviceAddAll(wf, how, id, fn, props?) targets every step. adviceRemove / adviceRemoveAll remove by id.
  • Stacking: most recently added is outermost, across both registries, unless depth (−100..100, default 0) overrides; lower depth is more outward. Re-adding an id replaces it.
  • Truthiness is Clojure's: only null, undefined and false are falsy. For after-while/after-until a step result is true when its "red/exit" is 0 or absent.
  • Advice is inherited through step embeds by flat step name; ancestor advice stacks outside child advice, and an ancestor entry with the same id replaces the child's.
  • advicePlan(wfOrChain, step) lists the composed stack outermost-first with {id, how, depth, seq, scope, level}.

7. YAML config and COLORS_PAR_*

Desired state is pure data in red.yml, parsed by Bun.YAML.parse (YAML 1.2: no is a string; app/… keys parse unquoted). Loaded keys land in opts unchanged, plus "red/state-file", the file's absolute path, so a package resolves relative paths against the file. Quote version-like values such as "3.10".

Every COLORS_PAR_<UPPER_SNAKE> environment variable is then overlaid onto the flat kebab-case key it names: COLORS_PAR_DO_TOKEN → do-token. The value is coerced to the type of the existing value (true/false for booleans, decimal integers for integers, otherwise a string). The namespace is shared by all three colors; there is no per-color prefix. Credentials live in these variables, never in the YAML file.

workdir: work      # relative to this file
message: hello
names:
  - alice
  - bob

8. Dry-run, progress, lifecycle

Optional helpers built on advice and plain steps; the engine knows nothing about them.

  • dryRun.advise(wf, steps) adds an around advice (id "red.dry-run/skip") to the listed side-effecting steps. When "red/dry-run" is set (by --dry-run) it logs dry-run: would run <step> (<event>) and skips the step.
  • progress.advise(wf) adds an all-step around advice (id "red.progress/progress") logging >>> <step> (<event>) on entry and <<< <step> (<n>ms) on exit.
  • lifecycle.preflight(opts, config, env?) is a reusable first step: merge defaults under opts, apply an optional overlay, run every validator (opts, env, {event, real}), and fail with exit 2 and all errors joined if any report; otherwise call afterValidate or return exit 0. real is false under dry-run.
  • Both advice helpers log through runtime.log, a mutable seam tests replace. red has no subprocess runner: steps spawn commands or call APIs themselves.

9. CLI and the ./red launcher

./red <event> [-f|--file red.yml] [--start step] [--end step] [--dry-run]
  • runCli(wf, args, config?) is the non-exiting, testable form: parse arguments, load the YAML, overlay COLORS_PAR_*, stamp "red/event" (and "red/dry-run"), apply --start/--end, run, and return the final opts. Usage, missing-file and parse errors return exit 2.
  • execCli(wf, args?, config?) prints "red/err" and "red/trace" to stderr and exits with "red/exit".
  • CliConfig: defaultFile (default red.yml), searchParents (find it in the nearest ancestor via findUp), allowedEvents (anything else is a usage error). Events are otherwise arbitrary strings.

A project's ./red is a self-contained, executable Bun script (#!/usr/bin/env bun) holding the steps, the workflow, its advice and the execCli call. Depend on red by a pinned version: a version-pinned npm specifier once published, until then a pinned git dependency in package.json; never an unpinned specifier.

10. The example

examples/hello is a small, offline package whose steps call local command-line tools:

hello/check  → hello/host → hello/greet (one branch per name) → hello/report
preflight      uname -sm    create: write <name>.txt             create: cat the files
                            delete: rm -f <name>.txt             delete: rmdir the workdir

Progress advice wraps every step; dry-run advice skips hello/greet and hello/report.

cd examples/hello
./red create --dry-run
./red create
COLORS_PAR_MESSAGE=hi ./red create
./red delete

11. Testing

  • bun test discovers test/*.test.ts. Engine, advice, CLI, dry-run, progress and lifecycle behaviour are tested in-process; tests capture logs by replacing runtime.log.
  • test/hello-example.test.ts drives the real examples/hello/red launcher as a subprocess: create, delete, dry-run, COLORS_PAR_* overlay, validation and command failure.
  • bun run typecheck runs tsc --noEmit. CI runs both on Bun 1.3.14.
